## Purpose

Define the official vocabulary control layer for SentinelOS.

This dictionary governs public wording, internal prompts, investor language, runtime terminology, UI labels, agent communication, compliance wording, website copy, and governance interpretation.

This document does not authorize runtime mutation, autonomous execution, public claims, external tenant activation, or deployment changes.

```txt
docs/governance/SENTINELOS_CONSTITUTION.md
```

Root principle:

```txt
SentinelOS is a governed execution operating framework.
```

All approved language must preserve:

- human authority
- governance supremacy
- advisory vs execution separation
- visible approval boundaries
- honest maturity claims
- modular architecture
- controlled operational execution

## Semantic Control Doctrine

Language is part of governance.

Terminology must not create false authority, maturity, autonomy, legal posture, or runtime capability.

Rule:

```txt
If a word implies execution, autonomy, replacement, certification, production readiness, legal authority, or self-authorization, it must be reviewed before use.
```

## Core Vocabulary Map

| Approved Term | Meaning | Avoid / Replace |
| --- | --- | --- |
| `governed execution` | action path controlled by policy, approval, and audit | autonomous execution |
| `operating framework` | structured system for orchestration, governance, and execution boundaries | simple GPT, chatbot |
| `orchestration` | coordinated workflow routing under governance | uncontrolled automation |
| `advisory intelligence` | analysis, recommendation, classification, and preparation | autonomous decision-maker |
| `approval continuity` | persistent approval state across pauses, reviews, and execution retries | informal approval |
| `execution boundary` | line between recommendation and authorized action | direct action |
| `command envelope` | structured intent package reviewed by governance | free-form instruction |
| `controlled operational execution` | execution under authority, approval, policy, and audit | independent action |
| `governance preflight` | required policy check before handler execution | post-action review |
| `audit receipt` | recorded proof of action, block, or decision | loose log |
| `runtime truth` | current verified live system state | assumption |
| `documentation truth` | documented current posture after verification | stale docs |
| `semantic control` | vocabulary discipline that prevents claim drift | branding copy |
| `face plane` | interaction layer over SentinelOS | standalone product |
| `policy layer` | rule and approval authority | suggestion layer |
| `human-authorized` | execution allowed by human authority where required | self-authorizing |

## Safe Governance Language vs High-Risk Language

| Safer Language | High-Risk Language | Rule |
| --- | --- | --- |
| orchestrate | control | Use `control` only when describing governance controls, not domination of external systems |
| prepare | execute | Use `execute` only when an approved execution path exists |
| coordinate | command | Use `command` for formal command envelopes only |
| recommend | perform | Use `perform` only after authorization is explicit |
| govern | enforce runtime | Use `enforce runtime` only when runtime enforcement exists and is verified |
| framework | autonomous system | Avoid autonomy claims unless capability classification supports it |
| guided execution | independent action | SentinelOS should not imply self-authorizing action |
| human-authorized | self-authorizing | Self-authorization is prohibited |
| approval-aware | approval-free | Avoid implying bypass |
| audit-visible | invisible automation | Audit visibility is required |
