# GBP Phase 4 — Deployment Profiles

## Purpose

Define controlled government specializations of the GBP without creating separate architectures.

## Principle

Each deployment profile inherits:

- core outcome engines,
- core governance policies,
- core evidence requirements,
- core executive workspaces,
- core authority boundaries,
- core audit and receipt expectations.

## Baseline Inheritance

Each deployment profile inherits from:

- the MOB constant,
- the active MOB overlay,
- the Government Deployment Blueprint baseline,
- applicable Executive and Board governance surfaces,
- applicable readiness, risk, evidence, and audit rules.

### Inheritance rules

- A profile is a specialization, not a fork.
- A profile may refine current operating posture without replacing source doctrine.
- A profile must remain compatible with inherited governance and proof rules.
- A profile may use overlays, addenda, and review-held current-state records.
- A profile must not discard inherited control boundaries.

## Profile Definition Areas

A deployment profile should define:

- mission context,
- operating environment,
- network and hosting assumptions,
- data sensitivity posture,
- authority model,
- readiness expectations,
- evidence and audit posture,
- executive and board reporting surfaces.

## Allowed Specialization Areas

Profiles may specialize:

- mission scope,
- environment constraints,
- sovereign or tenant boundary,
- reporting format,
- evidence presentation,
- MRI interpretation detail,
- approved integration surfaces.

## Non-Negotiable Inherited Controls

Profiles must preserve:

- approval boundaries,
- authority validation,
- risk evaluation,
- evidence traceability,
- audit receipt generation,
- proof-lane separation,
- non-authorization constraints,
- Executive Desk control-surface boundaries.

## Synchronization Requirements

Each profile must remain synchronized with:

- the MOB constant,
- the active MOB overlay,
- Board and Executive addenda,
- current evidence baseline,
- current readiness and verification posture.

Preferred drift remedies:

- addendum,
- overlay,
- profile refresh,
- review-held current-state update.

Drift must not be resolved by replacing the governing baseline.

## Proof Separation In Profiles

Deployment profiles must preserve proof-lane distinctions.

### Required lanes

- local proof,
- internal proof,
- public or external proof.

### Rules

- A profile may declare a capability locally verified without declaring it publicly proven.
- Internal readiness does not imply external release readiness.
- Profile claims must identify the lane in which proof was established.
- Executive, Board, and AI-facing profile views must preserve this distinction.

## Executive Desk Relationship

A deployment profile may define profile-specific Executive Desk presentation, but it must not alter the rule that the Executive Desk is a governed operating surface and not an unconstrained execution surface.

## Board Relationship

A deployment profile may define profile-specific Board reporting and oversight artifacts, but Board-facing specialization remains review-oriented and non-authorizing for protected mutating actions unless separately authorized.

## MRI Relationship

If a profile uses the MRI, it must expose readiness in a profile-compatible way while preserving baseline readiness doctrine.

A profile may specialize:

- readiness factor weighting,
- mission-specific readiness dimensions,
- profile-specific thresholds,
- reporting language.

A profile may not:

- hide blocked posture,
- suppress degraded factors,
- override freshness concerns,
- convert advisory interpretation into authority.

## AI Docking Relationship

If a profile supports AI-assisted operations, AI must dock through a governed control surface and not directly to uncontrolled runtime internals.

## Outcome

Phase 4 establishes deployment profiles as governed specializations of one inherited blueprint, kept current through overlays and addenda, synchronized with Executive and Board surfaces, and explicit about proof lanes.
